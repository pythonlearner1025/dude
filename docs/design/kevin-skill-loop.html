Kevin's Skill Loop

Code plays every game tick. DeepSeek picks the skill a few times a second. Opus writes the skills in Claude Code, minutes behind the action. Nothing learns from pixels.

Skill runtime

Runs the current skill once per game tick: aims, moves, fires. This is what makes Kevin look smooth and react within a frame, whatever the models are doing.

on events + ~1 Hz

Actor

DeepSeek with reasoning off. Reads a short state digest and answers with one line: a skill and its arguments, keep, or nofit. It never writes code.

~1.5 s

Voice

Unchanged: Gemma answers you out loud, told which skill Kevin is running so his words match his actions.

minutes, async

Coach

Opus in Claude Code on b650s, one ticket at a time. Writes and repairs skills, tests them on recorded traces, rewrites the actor's prompt, keeps memory.

a git repo

Skill library

Python skills with a one-line when each. The catalog the actor sees is built from them. Every change is a commit, so a bad skill rolls back.

per game

Body API

The only game-specific part: state (positions, enemies, cover, paths) and controls (move, aim, fire, crouch, grenade). Everything above it works for any game.

Recovery follows the same layers. Within a tick, the skill's own fallback handles it (blocked path: reroute). Within ~200 ms, the actor switches skills. Within minutes, the coach fixes the skill from the trace, and the fix applies next time, never mid-fight.

How the actor finds and runs skills

  1. Catalog. Each skill carries @skill(when=…, args=…, done=…). The runtime builds one line per skill from it: flank(target, side) — go around an enemy and hit it from the side; "flank", "go around".
  2. Loadout. Small models get worse as the menu grows, so the actor sees at most ~20 skills. That's a core set (follow, attack, take cover, hold fire…) plus the ones tagged for the moment: in combat, an order in force, a vehicle nearby. The coach curates the tags.
  3. Prompt. The rules, the loadout and worked examples form a stable prefix the provider caches. Only the state digest, events and orders change each step (~180 tokens).
  4. Call. The runtime parses the line leniently, checks the arguments (does elite#1 exist?), and starts the skill at the next tick, closing the old one. A malformed or impossible answer is re-asked once with the error, or the current skill keeps running.
  5. Feedback. A skill ends with Done(reason) or Failed(reason). That becomes the next event the actor reads, along with your lines, new enemies, damage, and a heartbeat about once a second. One request is in flight at a time; an answer that went stale while waiting is asked again.

What a skill looks like

A skill is a Python generator. It reads the body API, sets this tick's controls, and yields; the runtime calls it again next tick. It bounds itself in time, notices when it's stuck, and hands back control with a reason the actor can act on.

@skill(
    when='go around an enemy and hit it from the side: "flank", "go around", "hit them from the right"',
    args={"target": "enemy id", "side": "left or right"},
    done="the target is dead, or Kevin reached its side and engaged",
)
def flank(k, target, side="right"):
    deadline = k.time + 12.0
    while k.world.alive(target):
        if k.time > deadline:
            return Failed("flank took too long")
        if k.me.health < 0.25:
            return Failed("low health")              # the actor will pick take_cover
        enemy = k.world.enemy(target)
        spot = k.side_point(enemy.pos, k.player.pos, side, metres=12)
        if k.distance(k.me.pos, spot) > 2 and not k.stuck(seconds=2):
            k.move_toward(spot)
            k.aim_at(enemy.pos if enemy.visible else spot)
        else:
            return (yield from attack(k, target))      # from the side now
        yield                                           # end of this tick
    return Done("target down")

The instruction for writing skills

This lives as CLAUDE.md in the skill repo on b650s. The runtime starts claude -p with Opus 5.5 there, one ticket at a time.

# Kevin's skill library: instructions for the coach

You maintain the skills that play Kevin, the player's co-op teammate in Halo CE. A fast model
(DeepSeek V4.1 Flash) picks one skill at a time, a few times a second, from a catalog built from
this library; the runtime runs the picked skill every game tick (30 Hz). You are started with one
ticket (tickets/<id>.json). Resolve it, test, commit, and stop.

## What you may change
- skills/*.py: the skills.   actor/prompt.md: the actor's rules and worked examples.
- actor/loadouts.yaml: which skills the actor sees when.   tests/: scenarios and recorded traces.
- memory/: what Kevin knows about the player and the standing orders worth keeping.
Never change runtime/, body/ or anything outside this repository.

## The skill contract
- A skill is a generator decorated with @skill(when=..., args=..., done=...). It drives Kevin only
  through the body API `k` (body/API.md): read k.me, k.player, k.world; act with k.move_toward,
  k.aim_at, k.fire, k.crouch, k.jump, k.reload, k.grenade, k.melee; `yield` ends the tick.
- Yield every tick. Never sleep, block, do I/O, or keep state outside the generator.
- End with return Done(reason) or Failed(reason). The actor reads the reason, so make it say what
  happened in a few words ("low health", "target lost", "path blocked").
- Bound every skill: a time limit, stuck detection (no progress for 2 s), a lost target, low
  health. Where a cheap fallback exists (reroute, reposition, reload), do it instead of failing.
- Compose with `yield from other(k, ...)` rather than copying code. Keep skills under 60 lines.
- Keep the library small: extend or parameterise an existing skill before adding a near-duplicate.
  Remove skills nothing uses.
- The `when` line is all the actor sees. Write it for a fast model choosing in 200 ms: concrete,
  distinct from its neighbours, quoting the phrases players use for it. Under 120 characters.

## Tickets
- new_order: the actor said no skill fits an order. Write or extend a skill, and add the player's
  phrasing as a worked example in actor/prompt.md.
- failure: a skill failed, stalled or got Kevin killed more than once. Find the cause in the
  attached trace, fix it, and add the trace as a regression test.
- correction: the player told Kevin he got something wrong ("stop running in front of me"). Fix
  whichever caused it: the skill, the loadout, or the actor's rules.
- pattern: the actor keeps issuing the same sequence. Make it one skill if that saves decisions.
- review (every few minutes of play): read the session's decisions and outcomes. Add examples for
  the actor's repeated mistakes, consolidate memory/, keep every loadout under 20 skills.

## Before you finish
1. python -m kevin.skilltest: every skill runs on the recorded traces and simulated scenarios
   without exceptions, yields every tick and ends within its limits; your skill passes its test.
2. python -m kevin.catalog --check: the catalog builds; `when` lines are unique and short.
3. Commit, naming the ticket. The runtime loads the commit at the next skill boundary, and rolls
   a skill back by itself if it raises in play.
4. Write tickets/<id>.result.md: two sentences for the session log.

When a skill gets written or changed

  • The actor answers nofit: an order no skill covers.
  • A skill raises, stalls, or Kevin dies in it more than once.
  • You correct Kevin out loud.
  • The actor repeats the same sequence of calls.
  • A review every few minutes of play, and at a new level or enemy type.

Opus is never in the hot path. Its fixes land minutes later and apply next time. The cost is that an order nothing covers gets the nearest skill first, and Voice should say so ("I'll try").

Building it

  1. Runtime and library: the @skill decorator, a generator runner, the catalog and loadouts, hot reload from git, traces of every tick and decision.
  2. First body: single player. Halo's own AI already drives the companion through ~17 actions (follow, go to, shoot, cover, hold fire). Wrapping them as the body API lets us test the whole loop without new game code.
  3. Actor client: OpenRouter pinned to Together, reasoning off, the lenient parser, the triggers.
  4. Coach: the ticket queue and a claude -p worker on b650s (its Claude Code is 2.0.1, so it needs an update and a login). Opus writes the first dozen skills from the actions.
  5. Score it on the failures from the fifth playtest: get in front of me, hold fire, get behind that rock, flank right.
  6. Then co-op: a player-2 body API in Kevin's own game (state out, per-tick controls in), so the same skills drive him with your keyboard-and-mouse action space.
